## 3. FastIO vs Direct IO

- 목적: "중첩 IO가 항상 빠르다"는 통념을 크기별로 검증한다.
- 방법: 소켓 송신 버퍼를 0(중첩 IO/Direct IO)과 비0(커널 버퍼 복사/FastIO) 사이에서 토글하고, 작은 메시지와 큰 메시지에서 각각 `WSASend` 리턴 시간과 GQCS 처리량(TPS)을 측정.
- 결과 요약:

| 메시지 크기 | 유리한 방식 | 이유 |
|---|---|---|
| 작은 메시지 | FastIO | 커널 버퍼로 복사하는 비용이, 중첩 IO의 IRP 생성·페이지 잠금·IO 큐 처리 비용보다 작음 |
| 큰 메시지 | Direct IO(중첩 IO) | 메시지가 커지면 복사 비용이 커져, 유저 버퍼를 직접 잠그는 방식이 유리 |

- 메시지 크기와 copy 비용의 관계: "복사 비용 대 IRP·페이지 잠금 비용"의 균형이 크기에 따라 바뀐다. 작으면 복사가 싸고, 커지면 복사가 비싸진다.
- 테스트 환경 보정: 송신 방식만 비교하려면 클라이언트 수신 병목을 배제해야 한다. 측정 중 더미의 수신 병목이 결과에 섞이는 것을 확인하고, 클라이언트 수와 데이터 크기를 조정해 비교 대상 외 변수를 통제했다(자세한 과정은 `docs/Troubleshooting.md`).
- 참고: 라이브러리 본체는 송신 버퍼를 0으로 고정한다. 값을 토글하며 측정한 별도 테스트 프로그램은 이 레포에 코드로 포함되어 있지 않다(측정 자료 기준).
- 구체적인 크기별 처리량·리턴 시간 수치는 자료 판독 후 채웁니다. (TODO)

- **무중단 테스트**: 채팅 서버 7일 무중단, 게임 서버 7일 연결. 장시간 동안 세션 누수·크래시 없이 유지되는지 확인.

## 5. 결론

- 하나의 네트워크 라이브러리를 성격이 다른 여러 서버(채팅 싱글/멀티/인증·로그인·모니터링·게임)에서 검증해, 안정성과 확장성을 함께 확인했다.
- "중첩 IO가 항상 빠르다"가 아니라 메시지 크기에 따라 최적 송신 방식이 다르다는 점을 측정으로 확인했다.
- 측정 과정에서 서버가 아니라 측정 도구(더미 클라이언트)가 병목이 되는 상황을 발견하고 보정해, 측정 환경 자체의 공정성까지 데이터로 검증했다.
