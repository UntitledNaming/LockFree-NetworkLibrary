# Troubleshooting

이 문서는 문제를 어떻게 발견하고 원인을 어디까지 좁혔는지를 정리합니다. "고쳤다"로 끝내지 않고 분석 과정을 남깁니다. 아래 사례들은 주로 FastIO/Direct IO 측정 과정에서 나온 관찰 기록(`docs/servertest_results/ZeroCopy Test/테스트 고찰.txt`)에 근거합니다.

---

## 1. 더미 클라이언트 recv 병목

- 증상: 서버 GQCS 처리량(TPS)이 초반에는 높다가 어느 순간 확 떨어져 그 상태로 유지됨. 일시적인 하락이 아니라 지속적인 저하.
- 초기 가설: 서버 측 송신 처리나 세션 관리에 문제가 있어 처리량이 떨어지는 것으로 의심.
- 분석 과정:
  1. 서버 처리량이 떨어지는 순간에 멈춰서 상태를 확인하기 위해, 클라이언트 수신 여부를 표시하는 플래그를 두고 관찰.
  2. 확인 결과 일부 클라이언트 소켓만 수신을 하고, 다른 소켓들은 수신을 못 하고 있었음.
  3. 서버가 보낸 데이터를 클라이언트가 유저 영역에서 받아내지 못하면 TCP 수신 버퍼가 차고, window size가 0이 되어 서버가 더 보낼 수 없게 됨. 그러면 서버 송신의 완료 통지도 오지 않아 처리량이 떨어짐.
- 원인: 서버가 아니라 **측정 클라이언트(더미)의 수신 처리 능력**이 병목. 한 클라이언트 스레드가 수백 개 소켓의 수신을 다 감당하지 못함.
- 해결: 더미의 수신 처리 구조와 클라이언트 수를 조정해 송신량 대비 수신 처리 능력을 맞춤.
- 결과: 측정 클라이언트의 병목이 서버 처리량을 왜곡하지 않는 조건에서 다시 측정.
- 배운 점: 성능 측정은 서버뿐 아니라 측정 도구의 병목까지 함께 봐야 결과를 신뢰할 수 있다.

## 2. TCP window size 0으로 인한 서버 GQCS TPS 하락

- 증상: 서버 송신이 어느 순간 진행되지 않고, GQCS 처리량이 낮게 유지됨.
- 초기 가설: 서버 송신 로직(SendPost/WSASend)의 문제로 의심.
- 분석 과정:
  1. 송신 버퍼를 0으로 둔 상태에서는 `WSASend` 완료가 상대 ACK를 받아 내 버퍼를 놓을 수 있는 시점을 의미함을 확인.
  2. 클라이언트가 수신을 못 하면 상대 TCP 수신 버퍼가 차서 window size가 0이 되고, 서버는 더 보낼 수 없어 완료 통지가 오지 않음.
  3. 즉 서버 송신 로직의 문제가 아니라, 상대의 수신 정체가 서버 송신을 막는 구조.
- 원인: 클라이언트 수신 정체 → TCP window 0 → 서버 송신 완료 통지 중단 → 처리량 하락.
- 해결: 1번과 동일하게 클라이언트 수신 처리를 보정해 window가 0으로 가지 않도록 함.
- 결과: 송신 완료 통지가 정상적으로 이어지며 처리량 회복.
- 배운 점: 송신 버퍼를 0으로 둔 중첩 IO에서는 완료 통지가 상대 수신 상태와 직접 연결되므로, 처리량 하락을 서버 탓으로만 볼 수 없다.

## 3. select readset 루프 종료 조건 문제

- 증상: 더미의 일부 소켓만 수신이 처리되고 나머지는 계속 처리되지 않음.
- 초기 가설: 수신 처리량 부족(1번)만으로 보였으나, 특정 소켓만 편향되는 점이 이상했음.
- 분석 과정:
  1. 더미가 소켓을 일정 개수(예: 64개) 단위로 readset에 등록한 뒤 select를 걸고 수신하는 구조임을 확인.
  2. 첫 번째 루프에서는 조건에 걸려 정상적으로 끊고 수신하지만, 두 번째 루프부터는 등록 개수 기준으로 끊어야 할 조건이 의도대로 동작하지 않아, 계속 돌다가 최대치에 도달해서야 탈출.
  3. 그 결과 앞쪽 소켓만 반복 등록·수신되고 뒤쪽 소켓은 수신 기회를 못 얻음.
- 원인: readset 등록 루프의 종료 조건이 두 번째 루프부터 의도와 다르게 동작(등록 개수 기준으로 끊지 못함).
- 해결: 남은 소켓만 돌게 하거나 등록 개수 단위로 정확히 끊도록 루프 조건을 수정.
- 결과: 소켓들이 고르게 수신 처리됨.
- 배운 점: 측정 코드의 사소한 루프 조건이 전체 측정 결과를 왜곡할 수 있다.

## 4. FastIO / Direct IO 측정 환경 보정

- 증상: 송신 방식(FastIO/Direct IO)만 비교하려는데, 결과에 클라이언트 수신 병목이 섞여 방식 간 차이가 명확히 보이지 않음.
- 초기 가설: 송신 방식 자체의 차이로 해석하려 했으나, 수신 병목이 개입한 정황.
- 분석 과정:
  1. 더미가 무한 루프로 송신량을 크게 만들어, 세션 수보다 초당 메시지량이 훨씬 커지는 상황을 확인.
  2. 이 경우 한 클라이언트 스레드가 수백 개 소켓의 수신을 감당하지 못해 병목이 생기고, 이 병목이 송신 방식 비교에 개입.
  3. 실제 게임 트래픽은 유저 한 명이 초당 보내는 메시지가 제한적인데, 더미는 무한 루프라 메시지량이 과도했음.
- 원인: 비교 대상(송신 방식) 외 변수(클라이언트 수신 병목, 과도한 송신량)가 통제되지 않음.
- 해결: 클라이언트 수와 데이터 크기를 조정해, 송신 방식 비교에 필요한 조건만 남긴 뒤 측정.
- 결과: 크기별로 FastIO/Direct IO의 우열을 명확히 비교(자세한 결과는 `docs/Test_Report.md`).
- 배운 점: 비교 실험은 비교 대상 외 변수를 통제해야 결론이 유효하다.

## 5. send:recv 비율 보정

- 증상: 클라이언트 수가 많을 때 서버 송신 호출 비율과 클라이언트 수신 처리 비율이 크게 벌어짐.
- 초기 가설: 서버 성능 한계로 오인할 수 있었음.
- 분석 과정:
  1. 서버 Send 스레드가 한 소켓에 대해 매우 많은 송신을 하는 동안, 클라이언트 한 스레드는 수백 개 소켓의 수신을 다 처리해야 해서 비율이 맞지 않음.
  2. 클라이언트 수를 줄이면 클라이언트의 수신 횟수와 서버의 송신 횟수가 비슷해짐을 확인.
- 원인: 송신량 대비 클라이언트 수신 처리 능력의 불균형(세션 수보다 초당 메시지량이 병목).
- 해결: 클라이언트 수를 조정해 송신·수신 비율을 맞춤.
- 결과: 측정이 서버 성능을 반영하도록 조건을 정렬.
- 배운 점: 부하 테스트에서는 세션 수뿐 아니라 초당 메시지 생성량과 수신 처리 능력의 균형을 함께 봐야 한다.

## 6. 소켓 초기화 순서 오류 (WSAEOPNOTSUPP, 10045)

- 증상: 클라이언트 측에서 recv 등록 시 10045(WSAEOPNOTSUPP) 에러.
- 초기 가설: IOCP 등록이나 소켓 옵션 문제로 의심.
- 분석 과정: connect 전에 recv를 등록하고 있었음을 확인. 3-way handshake로 연결이 성립해야 수신을 받을 준비가 된 것이다.
- 원인: 소켓 준비 순서 위반(connect 전 recv 등록).
- 해결: 소켓 생성 → connect → IOCP 등록 → recv 등록 순서로 정정.
- 배운 점: 비동기 IO에도 상태 전제가 있다. 등록 API의 호출 시점은 프로토콜 상태와 맞아야 한다.

## 7. 접속 직후 DownClient 집중 발생 (백로그 큐)

- 증상: 루프백에서 다수 더미가 로그인 서버에 동시 접속하는 순간에만 DownClient가 집중 발생하고, 이후에는 발생하지 않음.
- 초기 가설: 네트워크 라이브러리 결함으로 의심했으나, 장시간 테스트 이력을 근거로 다른 원인을 탐색.
- 분석 과정: 3-way handshake 성공과 서버 백로그 큐 진입은 별개의 단계다. handshake에 성공해도 백로그 큐가 가득 차면 연결이 유실되어 클라이언트 쪽에서 DownClient로 관측될 수 있다.
- 원인: 동시 접속 폭주 시 백로그 큐 크기 부족.
- 해결: `listen`의 backlog 인자를 `SOMAXCONN_HINT(5000)`으로 지정해 큐 크기를 확장.
- 결과: 같은 테스트를 10회 반복해 초기 DownClient가 재발하지 않음을 확인.
- 배운 점: handshake 성공이 연결 수립을 보장하지 않는다. 접속 폭주 구간은 백로그까지 함께 봐야 한다.

## 8. 중복 로그인 오판 — RST 유실 가설의 대조 검증

- 증상: 원격(2대 머신) 환경에서만 로그인 서버의 중복 로그인 판정이 간헐적으로 오작동.
- 초기 가설: 클라이언트가 연결 종료 시 보내는 RST가 유실되어 서버에 이전 세션이 남는 것으로 추정. 다만 "RST 유실이 원인이라면 테스트 전반이 더 불안정해야 하지 않나"는 반론이 있었다.
- 분석 과정: 가설이 맞다면 패킷 유실이 사실상 없는 루프백 환경에서는 재현되지 않아야 한다. 동일 조건으로 루프백과 원격을 대조 테스트.
- 결과: 루프백 1시간 동안 미발생, 원격에서는 수십 초 내 재현. 가설을 뒷받침하는 근거를 확보.
- 배운 점: 재현 조건을 통제한 대조 실험으로 가설을 검증할 수 있다. 환경 변수(루프백/원격)를 분리하는 것이 핵심이었다.
