# Troubleshooting

이 문서는 문제를 어떻게 발견하고 원인을 어디까지 좁혔는지를 정리합니다. 

---

## 1. 부하 테스트 중 SendQ 폭증 / 송신 완료 통지 중단

- 증상: 부하 테스트 중 특정 시점부터 세션들의 SendQ(송신 큐)가 계속 쌓여 폭증. `WSASend`는 게시(post)되어 있는데 송신 완료 통지가 더 이상 오지 않음.
- 초기 가설: 서버 송신 로직(`SendPost`/`SendFlag`/`WSASend`)이나 세션 Lock 처리에 문제가 있는 것으로 의심.
- 분석 과정:
  1. 송신 로직을 점검하고, 세션 Lock을 쓰는 버전으로 바꿔 테스트했으나 동일하게 재현됨.
  2. 코드가 아니라 하드웨어를 의심해 네트워크 카드 등을 교체했으나 효과 없음.
  3. 완료 통지가 멈추는 지점을 추적했지만 코드·하드웨어 어느 쪽에서도 결정적 원인을 특정하지 못함.
- 원인: **미확정**. 코드와 하드웨어를 차례로 배제한 끝에 OS 내부 문제로 추정.
- 해결: OS를 재설치하자 같은 코드에서 더 이상 재현되지 않음.
- 결과: 이후 장시간 테스트에서 재발 없음.
- 배운 점: 코드·하드웨어를 하나씩 배제하는 대조 과정으로 원인 범위를 좁혔고, 재현이 사라진 뒤에도 "원인 미확정(OS 추정)"임을 과장 없이 그대로 남긴다.
---

## 2. 중복 로그인 오판 — RST 유실 가설의 대조 검증

- 증상: 원격(2대 머신) 환경에서만 로그인 서버의 중복 로그인 판정이 간헐적으로 오작동.
- 초기 가설: 클라이언트가 연결 종료 시 보내는 RST가 유실되어 서버에 이전 세션이 남는 것으로 추정. 다만 "RST 유실이 원인이라면 테스트 전반이 더 불안정해야 하지 않나"는 반론이 있었다.
- 분석 과정: 가설이 맞다면 패킷 유실이 사실상 없는 루프백 환경에서는 재현되지 않아야 한다. 동일 조건으로 루프백과 원격을 대조 테스트.
- 결과: 루프백 1시간 동안 미발생, 원격에서는 수십 초 내 재현. 가설을 뒷받침하는 근거를 확보.
- 배운 점: 재현 조건을 통제한 대조 실험으로 가설을 검증할 수 있다. 환경 변수(루프백/원격)를 분리하는 것이 핵심이었다.
