# Design Rationale

이 문서는 "왜 이렇게 설계했는지"를 정리합니다. 각 항목은 문제 상황 / 선택한 방식 / 대안 / 선택 이유 / 절충 / 검증 방법 순으로 적습니다. 코드 흐름의 상세는 `docs/Code_Flow.md`, 측정 결과는 `docs/Test_Report.md`를 참고하세요.

---


## 1. 왜 TLS 메모리 풀을 사용했는가

- 문제 상황: 여러 워커가 메시지 객체를 대량으로 할당·반납하면 힙에서 경합이 생긴다.
- 선택한 방식: 스레드별 서브풀(버킷 단위)로 락 없이 할당·반납. 버킷 교환만 공용 Lock-Free 스택 경유.
- 대안: 전역 new/delete, 단일 Lock-Free 풀.
- 선택 이유: 기본 new/delete도 LockFree 메모리 풀도 내부적으로 경합 처리가 들어간다. 그 경합 자체를 스레드 로컬로 배제하려는 것이다. 소유 ID로 잘못된 반납을 차단한다.
- 감수한 점: 스레드별 여유 노드가 메모리에 상주해 사용량이 늘고, 스레드 종료 시 반납 처리가 필요하다.
- 검증 방법: 모니터링의 풀 사용량 지표 관측.
- 관련 코드 흐름: TLS 메모리 풀 사용.

## 2. 왜 세션을 연결 끊김 즉시 반납하지 않는가

- 문제 상황: 끊김 확인 즉시 세션을 반납하면, Accept 스레드가 그 세션을 새 연결로 재사용한 뒤에 이전 IO의 실패 통지가 도착해 신규 세션을 오염시킨다. `closesocket`을 즉시 호출하면 핸들이 재사용되어 다른 세션에게 메시지를 보낼 수 있고, `OnClientLeave`를 즉시 호출하면 컨텐츠가 "끊긴 유저"로부터 이후 메시지를 받는 모순이 생긴다.
- 선택한 방식: 세션 수명 기준을 IO 개수가 아닌 "세션 메모리 사용 카운트(useCount)"로 두고, 사용하는 모든 경로가 사용 전 카운트를 올린다. 해제는 카운트를 0으로 만든 스레드가 담당하며, "카운트==0 확인"과 "해제 중 플래그(ReleaseFlag) 켜기"를 한 변수에 담아 128비트 CAS로 원자화한다. 카운트를 올린 뒤에도 세션 ID를 재검사해 재사용된 슬롯을 걸러낸다(이 확보 절차가 `SessionInvalid`).
- 대안: 세션별 락.
- 선택 이유: 이 문제는 동기화가 아니라 수명 기준의 문제라 세션에 락을 걸어도 해결되지 않는다. 목표는 여러 스레드가 동기화 객체 없이 동시에 세션을 쓰는 것이다. 사용은 자유롭게 두고 해제만 원자적 규칙으로 통제했다.
- 주의점: 세션 초기화 순서가 중요하다(새 값 세팅 → 세션 ID 변경 → 카운트 증가 → ReleaseFlag 해제는 마지막). Release 처리 중 컨텐츠 락과 겹치면 데드락이 가능해, Release는 PQCS로 워커 스레드에 위임한다. 
- 감수한 점: 세션을 쓰는 모든 경로에 확보/해제 절차가 들어가는 복잡도.
- 검증 방법: 장시간 접속/해제 반복 테스트에서 잘못된 세션 접근·누수 없음 확인.
- 관련 코드 흐름: 세션 생성/해제, SendPacket, Disconnect.

## 3. 왜 Send 스레드를 두는 버전을 추가했는가

- 문제 상황: 세션 락을 제거한 버전을 더미로 부하 테스트하자 TCP 재전송률이 크게 높아졌다. SendFlag 방식은 송신을 "보낼 수 있으면 바로 보내는" 구조라 전송량 자체를 조절할 수 없다.
- 선택한 방식: Send 전용 스레드를 두고, Config의 프레임 값에 따라 주기적으로 세션별 SendQ를 묶어 `WSASend`하는 버전을 추가했다. 네트워크 라이브러리 계층에서 버퍼링하는 것이다.
- 대안: SendFlag 즉시 송신 유지.
- 선택 이유: 프레임 단위 송신으로 바꾼 뒤 재전송률이 감소함을 확인했다. 
- 감수한 점: 더미에서 측정되는 평균 지연은 다소 늘어날 수 있다. 그래서 두 버전을 모두 유지한다.
- 검증 방법: 더미 부하 테스트에서 재전송률·지연 비교.
- 관련 코드 흐름: Send 스레드, SendPost.

> 위 설계 판단은 코드로 확인된 사실을 기준으로 정리했으며, 일부(네트워크-컨텐츠 분리·OnRecv 콜백 선택의 명시적 근거)는 재사용을 위한 자연스러운 선택에 가깝습니다. 관련 측정과 문제 해결 과정은 `docs/Test_Report.md`, `docs/Troubleshooting.md`를 참고하세요.
