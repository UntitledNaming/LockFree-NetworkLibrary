# Design Rationale

이 문서는 "왜 이렇게 설계했는지"를 정리합니다. 각 항목은 문제 상황 / 선택한 방식 / 대안 / 선택 이유 / 절충 / 검증 방법 순으로 적습니다. 코드 흐름의 상세는 `docs/Code_Flow.md`, 측정 결과는 `docs/Test_Report.md`를 참고하세요.

---

## 1. 왜 IOCP를 사용했는가

- 문제 상황: 다수 동시 접속을 적은 스레드로 처리해야 한다.
- 선택한 방식: IOCP + 워커 스레드 풀. 완료 포트 생성 시 concurrent 값을 러닝 스레드 수로 지정.
- 대안: select / WSAEventSelect, 스레드-퍼-커넥션.
- 선택 이유: select 계열은 소켓이 늘수록 전체를 훑는 비용이 커진다. IOCP는 완료된 IO만 큐로 받고, concurrent 값으로 동시에 깨어나는 워커 수를 조절해 불필요한 컨텍스트 스위칭을 줄일 수 있다.
- 감수한 점: 구현 복잡도가 높고, 중첩 IO의 완료 통지·수명 관리가 까다롭다.
- 검증 방법: 채팅·게임 서버 장시간 무중단 테스트, 모니터링 서버로 처리량 관측.
- 관련 코드 흐름: 서버 시작/초기화, Recv/Send 완료 처리.
- 관련 테스트: 장시간 무중단 테스트.

---

## 2. 왜 네트워크 라이브러리와 컨텐츠 서버를 분리했는가

- 문제 상황: 채팅·로그인·모니터링·게임 등 성격이 다른 서버가 같은 네트워크 처리를 필요로 한다.
- 선택한 방식: 네트워크 코어(`CLanServer`/`CNetServer`/`CGameLibrary`) + 컨텐츠는 콜백(`OnRecv` 등) 구현.
- 대안: 서버마다 네트워크 코드를 중복 작성.
- 선택 이유: 코어를 재사용해 컨텐츠에 집중하기 위함이다. 이 분리 덕분에 하나의 코어 위에 여러 검증용 서버를 올릴 수 있었다.
- 감수한 점: 콜백 계약이 고정되어 컨텐츠는 그 틀 안에서만 확장된다. 콜백 안에서 오래 걸리면 워커가 막힌다(채팅은 Job 큐로, 게임은 그룹 프레임으로 완화).
- 검증 방법: 실제로 채팅·로그인·모니터링·게임 서버를 같은 코어 위에 올려 검증.
- 관련 코드 흐름: OnRecv 콜백, 채팅/로그인/게임 흐름.

---

## 3. 왜 OnRecv 콜백 구조를 사용했는가

- 문제 상황: 라이브러리가 조립한 완성 패킷을 컨텐츠로 전달해야 한다.
- 선택한 방식: 순수가상 `OnRecv(sessionID, message)` 콜백.
- 대안: 컨텐츠가 직접 수신 루프를 도는 구조.
- 선택 이유: 라이브러리-컨텐츠 경계를 콜백으로 두면, 컨텐츠는 스트림 조립을 신경 쓰지 않고 완성된 패킷만 받는다. 일반적인 서버 프레임워크 패턴이기도 하다.
- 감수한 점: 콜백이 무거우면 워커가 막힌다. 그래서 채팅 싱글판은 Job 큐로 처리를 넘기고, 게임 서버는 그룹 프레임으로 분리한다.
- 검증 방법: 각 서버가 콜백 위에서 정상 동작하는지 장시간 테스트.
- 관련 코드 흐름: Recv 완료 처리, 채팅/게임 흐름.

---

## 4. 왜 세션 관리 구조를 이렇게 잡았는가

- 문제 상황: 세션을 빠르게 찾고, 재사용된 슬롯을 과거 세션과 구분해야 한다.
- 선택한 방식: 세션을 고정 배열로 두고 빈 인덱스를 Lock-Free 스택으로 관리. 세션 ID = 배열 인덱스(상위 비트) + 할당 ID(하위 비트).
- 대안: 해시맵(sessionID → 포인터), GUID.
- 선택 이유: 세션 ID에 인덱스를 실으면 조회가 시프트 한 번 + 배열 인덱싱으로 끝난다. 할당 ID로 재사용된 슬롯의 과거 요청을 걸러낸다. IOCP 완료 키에 세션 포인터를 직접 넣어 완료 처리에서 조회 자체를 생략한다.
- 감수한 점: 인덱스 비트폭이 최대 세션 수·할당 범위를 제한한다.
- 검증 방법: 장시간 접속/해제 반복에서 잘못된 세션 접근이 없는지 확인.
- 관련 코드 흐름: Accept, 세션 생성/해제.

---

## 5. 왜 TLS 메모리 풀을 사용했는가

- 문제 상황: 여러 워커가 메시지 객체를 대량으로 할당·반납하면 힙에서 경합이 생긴다.
- 선택한 방식: 스레드별 서브풀(버킷 단위)로 락 없이 할당·반납. 버킷 교환만 공용 Lock-Free 스택 경유.
- 대안: 전역 new/delete, 단일 Lock-Free 풀.
- 선택 이유: 기본 new/delete도 내부적으로 경합 처리(락)가 들어간다. 그 경합 자체를 스레드 로컬로 배제하려는 것이다. 소유 ID로 잘못된 반납을 차단한다.
- 감수한 점: 스레드별 여유 노드가 메모리에 상주해 사용량이 늘고, 스레드 종료 시 반납 처리가 필요하다.
- 검증 방법: 모니터링의 풀 사용량 지표 관측.
- 관련 코드 흐름: TLS 메모리 풀 사용.

---

## 6. 왜 Message / Buffer를 재사용했는가

- 문제 상황: 매 수신·송신마다 버퍼·메시지를 새로 만들면 할당/해제 비용과 경합이 크다.
- 선택한 방식: 수신은 세션별 링버퍼(`CRingBuffer`)로 재사용하고, 송신 메시지(`CMessage`)는 TLS 풀에서 할당·반납하며 참조 카운트로 여러 세션 전송을 공유한다.
- 대안: 요청마다 버퍼를 새로 할당.
- 선택 이유: 반복 할당을 없애고, 하나의 메시지를 여러 세션에 보낼 때 참조 카운트로 수명을 관리해 복제를 피한다.
- 감수한 점: 참조 카운트·풀 관리 로직이 필요하고, 반납 시점을 정확히 맞춰야 한다(송신 완료 시 반납).
- 검증 방법: 무중단·부하 테스트에서 메시지 누수·이중 반납 여부 확인.
- 관련 코드 흐름: Send 요청/완료, TLS 메모리 풀.

---

## 7. 왜 로그인/인증에 Redis를 사용했는가

- 문제 상황: 로그인 서버가 발급한 토큰을 컨텐츠 서버가 검증해야 한다.
- 선택한 방식: 로그인 서버가 Redis에 토큰을 저장하고, 인증 채팅 서버가 Redis에서 읽어 대조 후 삭제(1회용).
- 대안: DB에 토큰 저장, 서버 간 직접 통신.
- 선택 이유: key-value를 메모리에 바로 저장·조회하는 구조라 인증 토큰 저장소로 쓰기 편하다. 계정 정보 자체는 MySQL을 쓴다.
- 감수한 점: Redis 장애 시 인증 경로에 영향이 있고, 별도 인프라가 필요하다.
- 검증 방법: 채팅-로그인 인증 테스트.
- 관련 코드 흐름: 로그인/인증.
- 참고: P4 MMORPG 월드 서버는 Redis를 사용하지 않는다. 두 프로젝트의 Redis 사용 여부는 다르다.

## 8. 왜 모니터링 서버를 별도로 만들었는가

- 문제 상황: 여러 서버의 지표를 한곳에서 관찰해야 장시간 테스트가 의미 있다.
- 선택한 방식: 각 서버가 모니터링 클라이언트로 지표를 보내고, 중앙 모니터링 서버가 집계·저장.
- 대안: 각 서버가 개별적으로 지표를 파일에 남김.
- 선택 이유: 수집 창구를 하나로 두면 여러 서버의 상태를 함께 볼 수 있고, 각 서버는 보내기만 하면 된다.
- 감수한 점: 모니터링 서버 자체가 하나의 검증 대상이 되고, 지표 전송이 약간의 부하가 된다.
- 검증 방법: 장시간 테스트에서 지표 수집이 유지되는지 관측.
- 관련 코드 흐름: 모니터링 서버.

---

## 9. 왜 테스트 서버를 여러 개 만들었는가

- 문제 상황: 라이브러리가 성격이 다른 서버에서도 안정적으로 동작하는지 확인해야 한다.
- 선택한 방식: 채팅(싱글/멀티/인증)·로그인·모니터링·게임(에코) 등 여러 서버를 같은 코어 위에 올림.
- 대안: 하나의 서버(예: 에코)만으로 검증.
- 선택 이유: 서버마다 컨텐츠 처리 방식(단일 스레드 직렬, 락 병렬, 그룹/프레임)과 요구(인증, 지표 수집)가 달라, 여러 서버로 검증해야 라이브러리의 안정성과 확장성을 함께 볼 수 있다. 에코 서버는 그중 하나일 뿐이다.
- 감수한 점: 서버가 늘수록 유지·테스트 부담이 커진다.
- 검증 방법: 각 서버로 장시간·부하·비교 테스트 수행.
- 관련 코드 흐름: 채팅/로그인/모니터링/게임 흐름.

---

## 10. 왜 세션을 연결 끊김 즉시 반납하지 않는가

- 문제 상황: 끊김 확인 즉시 세션을 반납하면, Accept 스레드가 그 세션을 새 연결로 재사용한 뒤에 이전 IO의 실패 통지가 도착해 신규 세션을 오염시킨다. `closesocket`을 즉시 호출하면 핸들이 재사용되어 다른 세션에게 메시지를 보낼 수 있고, `OnClientLeave`를 즉시 호출하면 컨텐츠가 "끊긴 유저"로부터 이후 메시지를 받는 모순이 생긴다.
- 선택한 방식: 세션 수명 기준을 IO 개수가 아닌 "세션 메모리 사용 카운트(useCount)"로 두고, 사용하는 모든 경로가 사용 전 카운트를 올린다. 해제는 카운트를 0으로 만든 스레드가 담당하며, "카운트==0 확인"과 "해제 중 플래그(ReleaseFlag) 켜기"를 한 변수에 담아 128비트 CAS로 원자화한다. 카운트를 올린 뒤에도 세션 ID를 재검사해 재사용된 슬롯을 걸러낸다(이 확보 절차가 `SessionInvalid`).
- 대안: 세션별 락.
- 선택 이유: 이 문제는 동기화가 아니라 수명 기준의 문제라 세션에 락을 걸어도 해결되지 않는다. 락 방식은 특정 스레드의 독점을 의미하는데, 목표는 여러 스레드가 락 없이 동시에 세션을 쓰는 것이다. 사용은 자유롭게 두고 해제만 원자적 규칙으로 통제했다.
- 주의점: 세션 초기화 순서가 중요하다(새 값 세팅 → 세션 ID 변경 → 카운트 증가 → ReleaseFlag 해제는 마지막). 해제 처리 중 컨텐츠 락과 겹치면 데드락이 가능해, 해제는 PQCS로 워커 스레드에 위임한다. 빠른 종료가 필요하면 `CancelIoEx`로 걸린 IO를 취소해 실패 통지를 앞당긴다.
- 감수한 점: 세션을 쓰는 모든 경로에 확보/해제 절차가 들어가는 복잡도.
- 검증 방법: 장시간 접속/해제 반복 테스트에서 잘못된 세션 접근·누수 없음 확인.
- 관련 코드 흐름: 세션 생성/해제, SendPacket, Disconnect.

## 11. 왜 Send 스레드를 두는 버전을 추가했는가

- 문제 상황: 세션 락을 제거한 버전을 더미로 부하 테스트하자 TCP 재전송률이 크게 높아졌다. SendFlag 방식은 송신을 "보낼 수 있으면 바로 보내는" 구조라 전송량 자체를 조절할 수 없다.
- 선택한 방식: Send 전용 스레드를 두고, Config의 프레임 값에 따라 주기적으로 세션별 SendQ를 묶어 `WSASend`하는 버전을 추가했다. 네트워크 라이브러리 계층에서 버퍼링하는 것이다.
- 대안: SendFlag 즉시 송신 유지.
- 선택 이유: 프레임 단위 송신으로 바꾼 뒤 재전송률이 감소함을 확인했다. (구체 수치는 원자료 확인 후 기재. TODO)
- 감수한 점: 더미에서 측정되는 평균 지연은 다소 늘어날 수 있다. 그래서 두 버전을 모두 유지한다.
- 검증 방법: 더미 부하 테스트에서 재전송률·지연 비교.
- 관련 코드 흐름: Send 스레드, SendPost.

> 위 설계 판단은 코드로 확인된 사실을 기준으로 정리했으며, 일부(네트워크-컨텐츠 분리·OnRecv 콜백 선택의 명시적 근거)는 재사용을 위한 자연스러운 선택에 가깝습니다. 관련 측정과 문제 해결 과정은 `docs/Test_Report.md`, `docs/Troubleshooting.md`를 참고하세요.
