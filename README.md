# IOCP 네트워크 라이브러리

## 1. 프로젝트 개요

C++ IOCP를 기반으로 네트워크 라이브러리와 게임 라이브러리를 직접 구현하고, 그 위에 여러 테스트 서버를 올려 안정성과 확장성을 검증한 프로젝트입니다. 특정 게임 로직을 만드는 것이 목적이 아니라, 다양한 서버가 공통으로 쓸 수 있는 네트워크 서버 프레임워크를 구현하고 장시간 테스트로 검증하는 것이 목표입니다. 검증에는 채팅, 로그인, 모니터링, 게임(에코) 등 여러 서버를 사용했으며, 에코 서버는 라이브러리를 확인하기 위한 검증용 서버 중 하나입니다.

## 2. 전체 포트폴리오에서의 역할

이 프로젝트는 포트폴리오의 대표 프로젝트 중 하나입니다. 앞선 기반 기술 프로젝트에서 다룬 멀티스레드 동시성(Lock-Free 자료구조)과 성능 측정·최적화(A* 최적화) 위에, IOCP 기반 네트워크 서버 프레임워크를 구현한 단계에 해당합니다. 여기서 만든 `network_library` / `game_library` / `common_files`는 이후 P4 MMORPG 월드 서버의 기반 라이브러리로 그대로 사용됩니다.

## 3. 핵심 구현

| 영역 | 내용 |
|---|---|
| IOCP / GQCS | 완료 포트 생성 시 러닝 스레드 수로 concurrent 값을 지정, Worker 스레드가 GQCS로 완료를 받아 Recv / Send / 세션 해제로 분기 |
| Accept / Worker / Send Thread | Accept 스레드가 연결 수락·세션 등록, Worker 스레드 풀이 IO 처리. Send 스레드는 Config로 On/Off 가능(선택적) |
| 세션 관리 | `CSession` 기반. 세션 배열(SessionTable)과 인덱스를 Lock-Free 스택으로 관리, 세션 ID에 배열 인덱스와 할당 ID를 함께 인코딩 |
| Send / Recv 처리 | 수신은 링버퍼로 조립, 송신은 세션별 Lock-Free 큐에 모아 세션당 하나의 WSASend만 유지 |
| OnRecv 콜백 | 라이브러리가 조립한 패킷을 컨텐츠 서버의 `OnRecv` 콜백으로 전달(라이브러리-컨텐츠 분리) |
| 세션 수명 | 참조 카운트와 릴리즈 플래그를 128비트 CAS로 함께 처리해 세션 Lock 없이 안전하게 해제 |
| TLS 메모리 풀 | 스레드별 풀로 메시지 객체 할당 경합을 줄이고, 풀 소유 ID로 잘못된 반납을 차단 |
| Buffer / Message 재사용 | 직렬화 버퍼(Message)와 링버퍼를 풀·재사용 구조로 관리 |
| game_library | 네트워크 코어 위에 그룹(CGroup)·프레임 스레드·그룹 이동을 얹은 게임 라이브러리 |
| Monitoring | 각 서버가 지표를 수집해 모니터링 서버로 전송, PDH 기반 프로세스 지표 포함 |

네트워크 헤더 처리에 따라 두 종류의 서버 코어를 제공합니다. LAN 환경용은 헤더가 길이 정보만 있고, 외부(Net) 환경용은 패킷 코드·체크섬·인코딩(난독)을 포함합니다.

## 4. 서버 구조

네트워크 라이브러리와 컨텐츠 서버를 분리했습니다. 라이브러리는 IOCP·세션·송수신을 담당하고, 각 서버는 콜백만 구현해 그 위에 올라갑니다.

```
LockFree-NetworkLibrary/
├─ network_library/     # 네트워크 코어 (LAN/Net 서버, 세션, 클라이언트)
├─ game_library/        # 게임 라이브러리 (그룹/게임 세션/유저 인터페이스)
├─ common_files/        # 공용 (링버퍼, 메시지, TLS 메모리 풀, Lock-Free, 로그, PDH 등)
├─ protocol/            # 서버 공통 프로토콜
├─ servers/             # 라이브러리를 검증하는 서버들
│   ├─ chatserver/              # 채팅 서버 (싱글 스레드)
│   ├─ chatserver_multi_ver/    # 채팅 서버 (멀티 스레드)
│   ├─ chatserver_auth_ver/     # 채팅 서버 (로그인 연동/인증)
│   ├─ loginserver/             # 로그인 서버
│   ├─ monitoringserver/        # 모니터링 서버
│   └─ gameserver/              # 게임 라이브러리 적용 게임(에코) 서버
├─ clients/             # 모니터링 클라이언트
├─ dummy/               # 부하 테스트용 더미 프로그램
├─ DB/                  # DB 스키마
└─ redis/              # Redis 실행 파일
```

## 5. 주요 코드 흐름

README에서는 핵심 흐름만 요약합니다. 함수 단위 상세는 `docs/Code_Flow.md`로 정리합니다.

- **서버 시작 / 초기화**: 컨텐츠 서버가 라이브러리 `Start`를 호출 → IOCP 생성·세션 테이블 준비 → 리슨 소켓 준비 → Worker/Accept(선택적 Send) 스레드 생성.
- **Accept**: 연결 수락 → 세션 인덱스 확보 → 세션 ID 생성 → 소켓을 IOCP에 등록(완료 키로 세션 지정) → 첫 수신 등록.
- **Recv 완료 처리**: GQCS로 수신 완료 수신 → 링버퍼에서 패킷 조립 → `OnRecv` 콜백 → 다음 수신 등록.
- **Send 요청 / 완료 처리**: 컨텐츠가 보낸 메시지를 세션 송신 큐에 넣고 세션당 하나의 WSASend만 유지 → 완료 시 메시지 반납 후 남은 큐를 이어서 전송.
- **세션 해제**: 참조 카운트가 0이 되는 시점을 128비트 CAS로 판별해 중복 해제 없이 안전하게 반납.
- **TLS 메모리 풀 사용**: 메시지·노드 객체를 스레드별 풀에서 할당/반납해 경합을 줄임.
- **OnRecv 콜백을 통한 컨텐츠 분리**: 라이브러리는 패킷 조립까지만, 컨텐츠 처리는 각 서버가 콜백에서 담당.

## 6. FastIO vs Direct IO 비교

중첩(Overlapped) IO가 항상 빠르다는 통념이 실제로 맞는지 확인하기 위해, 소켓 송신 버퍼 사용 여부(FastIO / Direct IO)를 메시지 크기별로 측정했습니다.

| 메시지 크기 | 유리한 방식 | 이유 |
|---|---|---|
| 작은 메시지 | FastIO | 데이터를 커널 송신 버퍼로 복사하는 비용이, 중첩 IO의 IRP 생성·페이지 잠금·IO 큐 처리 비용보다 작음 |
| 큰 메시지 | Direct IO(중첩 IO) | 메시지가 커지면 복사 비용이 커져, 유저 버퍼를 직접 잠그는 방식이 유리 |

결론은 "중첩 IO가 항상 빠르다"가 아니라, **메시지 크기와 복사 비용에 따라 최적 송신 방식이 달라진다**는 것입니다. WSASend 리턴 시간과 GQCS 처리량(TPS)을 지표로 사용했습니다. (구체적인 크기별 TPS 수치는 정리 중입니다. TODO)

## 7. 안정성 테스트

여러 서버를 장시간 구동하며 무중단·연결 안정성을 확인했습니다.

| 테스트 | 목적 | 결과 |
|---|---|---|
| 채팅 서버 무중단 | 장시간 세션 처리 안정성 | 7일 무중단 |
| 게임 서버 연결 | 게임 라이브러리 적용 서버 장시간 연결 | 7일 연결 |
| 채팅-로그인 인증 | 로그인/인증 연동 안정성 | 5일 인증 테스트 |
| 싱글/멀티 채팅 비교 | 컨텐츠 처리 방식별 성능 비교 | 싱글(작업 큐 직렬) vs 멀티(락 기반 병렬) 비교 (세부 수치 TODO) |
| 모니터링 지표 수집 | TPS·CPU·메모리·TCP 재전송 관측 | 모니터링 서버로 지표 수집 |

부하는 더미 클라이언트로 생성했으며, 측정 지표는 모니터링 서버로 모아 관찰했습니다.

## 8. 주요 트러블슈팅

### 더미 클라이언트 recv 병목으로 인한 서버 처리량 하락
- 증상: 서버 GQCS 처리량(TPS)이 높다가 어느 순간 확 떨어져 유지됨.
- 원인: 더미 클라이언트 한 스레드가 수백 개 소켓의 recv를 다 처리하지 못하자 TCP 수신 버퍼가 차고, window size가 0이 되어 서버 송신이 완료 통지를 받지 못함. 즉 서버가 아니라 측정 클라이언트가 병목.
- 해결: 더미의 recv 처리 구조와 클라이언트 수를 조정해 send:recv 비율을 맞추고, 측정 환경 자체의 공정성을 확보.
- 배운 점: 성능 측정은 서버뿐 아니라 측정 도구의 병목까지 함께 봐야 결과를 신뢰할 수 있음.

### select readset 루프 종료 조건 문제
- 증상: 더미의 일부 소켓만 recv가 처리되고 나머지는 처리되지 않음.
- 원인: readset에 소켓을 64개 단위로 등록해야 하는데, 루프 종료 조건이 두 번째 루프부터 의도대로 끊기지 않아 등록·수신이 편향됨.
- 해결: 등록 개수 기준으로 루프를 나눠 남은 소켓도 고르게 처리하도록 수정.
- 배운 점: 측정 코드의 사소한 루프 조건이 전체 측정 결과를 왜곡할 수 있음.

### FastIO / Direct IO 측정 환경 보정
- 증상: 송신 방식만 비교하려는데 클라이언트 수신 병목이 결과에 섞임.
- 원인: 더미가 무한 루프로 송신량을 크게 만들어, 세션 수보다 초당 메시지량이 병목이 됨.
- 해결: 클라이언트 수와 데이터 크기를 조정해 송신 방식 비교에 필요한 조건만 남긴 뒤 측정.
- 배운 점: 비교 실험은 비교 대상 외 변수를 통제해야 결론이 유효함.

> 위 트러블슈팅의 관찰 기록은 측정 자료(ZeroCopy 테스트 고찰)에 근거합니다. 더미 클라이언트 소스는 이 레포에 실행 파일·로그 형태로만 포함되어 있어, 관련 코드 근거는 측정 문서 기준입니다. (확인 필요)

## 9. Redis / DB

- 이 프로젝트는 로그인/인증 경로에서 Redis를 사용합니다. 로그인 서버가 세션 토큰을 Redis에 저장하고, 인증 버전 채팅 서버가 이를 조회·검증한 뒤 삭제하는 1회용 토큰 구조입니다. `servers/loginserver`, `servers/chatserver_auth_ver`에서 `cpp_redis` 라이브러리를 사용합니다.
- 계정·로그 데이터는 MySQL을 사용하며 스키마는 `DB/` 폴더에 있습니다.
- P4 MMORPG 월드 서버는 Redis를 사용하지 않습니다. 두 프로젝트의 Redis 사용 여부는 서로 다릅니다.

## 10. P4 MMORPG 서버와의 관계

- 이 프로젝트에서 구현한 `network_library` / `game_library` / `common_files`는 P4 MMORPG 월드 서버의 기반 라이브러리로 그대로 사용되었습니다.
- P4는 이 기반 위에 AOI(관심 영역), 이동 동기화, 서버 권위 전투, 몬스터 AI, 아이템, 비동기 DB 저장 구조를 붙인 실제 MMORPG 서버 프로젝트입니다.
- 이 레포의 게임(에코) 서버는 게임 라이브러리를 검증하기 위한 서버이며, P4의 직접 전신이 아닙니다. 두 프로젝트는 같은 게임 라이브러리를 공유하는 관계입니다.

## 12. Build & Run

- 환경: Windows, Visual Studio 2022, C++17
- 네트워크: WinSock2 / IOCP
- 의존성: Redis(로그인/인증 테스트 시), MySQL(계정·로그 DB)
- 실행 요약:
  - 모니터링 서버를 먼저 구동한 뒤 대상 서버를 구동합니다.
  - 채팅 서버 단독 테스트는 채팅 서버를, 로그인 연동 테스트는 인증 채팅 서버·로그인 서버·Redis를 함께 구동합니다.
  - 게임 서버 테스트는 게임 서버를 구동합니다.
  - 서버 IP·Port·DB·Redis 접속 정보는 각 서버의 Config 파일에서 설정합니다.

## 13. 개선 방향

- 더 다양한 네트워크 부하 패턴(메시지 크기·빈도 분포)으로 측정 범위 확대
- 메시지 크기에 따라 송신 방식(FastIO / Direct IO)을 자동 선택하는 정책 검토
- TLS 메모리 풀 사용량·경합 통계의 시각화
- 모니터링 지표를 한눈에 보는 대시보드 개선
- Linux epoll 기반 버전과의 비교 (확인 필요)
